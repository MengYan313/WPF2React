# WPF→React 迁移评价指标规范

- 规范版本：1.0
- 适用项目版本：W2MR 4.4
- 文档性质：项目实现与实验执行规范
- 相关实现：`src/migration/evaluation/`

本文定义 WPF2React 当前已经实现的迁移评价指标、计算方式、分类逻辑、结果解释和适用边界。本文属于项目文档，不修改或替代 `docs/02_前端UI迁移研究稿.md` 等研究背景材料；研究文档用于说明论文方向，实际评测以本规范和当前代码为准。

## 1. 评价目标

迁移质量不能由一个“是否成功”布尔值完整描述。当前项目将评价拆成两个互补层级：

1. **工程可用性层**：回答迁移产物是否能被定位、编译，以及多个页面之间的调用接口是否能按预先冻结的关系运行。
2. **用户可见质量层**：回答迁移后页面在静态截图中对原页面的组件、布局、样式和内容还原程度，以及目标页面自身的视觉完成度。

第一层偏向客观、可执行、可重复验证；第二层偏向用户看到的页面质量，但依赖多模态模型判断并具有一定主观性。两层必须分别报告，不能用视觉高分掩盖编译失败，也不能用编译通过推导视觉或交互等价。

### 1.1 为什么每个层级可以有多个指标

“层级”表示评价对象和验证深度，“指标”表示该层级内需要回答的具体问题。一个层级可以并且通常应该包含多个指标。例如，组件编译成功率说明有多少组件完成了最低可用迁移，但不能区分失败来自“没有找到目标组件”还是“找到了但代码无法编译”；因此需要缺失率和编译失败率作为诊断指标。

本项目采用以下组织方式：

| 类别 | 用途 | 示例 |
| --- | --- | --- |
| 主指标 | 直接回答该层级是否达到目标 | C-CPR、P-CPR、PECTPR、Overall Fidelity |
| 分项指标 | 描述一个复合目标的不同方面 | Component/Layout/Style/Content Fidelity |
| 诊断指标 | 解释主指标为什么降低 | C-MR、C-CFR、失败状态计数、问题类别 |
| 覆盖率 | 判断主指标是否基于完整样本 | Call Test Coverage、Visual Pair Coverage |
| 评测器状态 | 区分迁移失败与评测环境故障 | EVALUATOR_ERROR、INVALID_COMPARISON |

这种分类可以同时保持结论简洁和失败可解释性：论文或报告可用少量主指标比较方法，再用分项、诊断和覆盖率定位差异来源。

## 2. 通用计算原则

### 2.1 Ground Truth 与固定分母

正式评测前先从原 WPF 项目确定性抽取页面、组件和页面调用关系，人工核验后冻结为 Ground Truth（GT）清单。迁移方法只能读取正常迁移输入，不能读取评测断言、参考目标代码或人工标签。

各主指标使用冻结 GT 作为固定分母：

- 组件指标分母是 GT 组件实例总数；
- 页面指标分母是 GT 页面总数；
- 页面调用指标分母是 GT 调用边总数；
- 视觉指标分母是人工登记的 GT 截图对总数。

固定分母可以避免某种迁移方法通过少生成页面、跳过复杂组件或少配置测试来人为提高成功率。

### 2.2 迁移失败与评测器错误分离

以下情况属于迁移结果失败：

- GT 组件或页面在目标代码中缺失；
- 目标代码被找到但 TypeScript 编译失败；
- 调用测试正常执行但断言失败；
- 可比较截图中出现明显视觉差异。

以下情况属于评测器错误或样本不可用：

- 本地缺少 `tsc`、`tsconfig.json` 或测试运行器；
- 命令超时、入口路径错误或模型请求失败；
- 截图损坏、截图不是同一页面或不是同一状态。

评测器错误不得被计为迁移失败，否则会把实验环境问题错误归因给迁移方法。当前实现会将受影响的主指标设为 `null`，并保留具体错误证据。

### 2.3 逐项证据优先于单一总分

每个组件、页面、调用边和截图对都保留独立状态与证据。汇总指标仅用于总体比较；失败分析、人工复核和论文案例研究必须回到逐项 JSON/JSONL 记录。

## 3. 工程可用性层

工程可用性层继续细分为组件、单页面和多页面调用三个递进子层。后一个子层不会替代前一个子层：页面编译通过不能证明每个源组件都被正确定位，调用接口通过也不能证明页面视觉忠实。

## 3.1 组件编译层

### 3.1.1 评价单位与判别过程

评价单位是原 WPF 控件树中的**组件实例**，而不是去重后的控件类型。两个页面各有一个 `Button` 时，应当形成两个 GT 实例。`component_id` 使用稳定的 `page_id:node_path`，例如 `MainWindow:root.0.2`。

每个组件依次经过两个判定阶段：

1. **组件定位判别器**：根据页面路径、目标文件提示、导出符号、MUI 映射、JSX 标签、源名称和可见文本等证据搜索目标实现。同一个 JSX occurrence 不会重复分配给多个源组件。
2. **编译判定**：若定位到目标实现，则编译承载该实现的 TS/TSX 入口及其依赖；退出码为 0 才视为编译通过。

定位判别器是可替换接口。后续可以接入 LLM 辅助搜索复杂重命名或跨文件重组，但 LLM 只能负责“找到候选实现”，最终成功仍由编译器裁决。

### 3.1.2 互斥状态

| 状态 | 含义 | 是否属于迁移失败 |
| --- | --- | --- |
| `NOT_FOUND` | 未找到对应目标实现 | 是 |
| `AMBIGUOUS` | 多个候选无法唯一确定 | 是，正式评测前也可转人工复核 |
| `COMPILE_FAILED` | 找到实现，但编译器返回非零退出码 | 是 |
| `COMPILE_PASSED` | 找到实现且编译通过 | 否 |
| `EVALUATOR_ERROR` | 编译器缺失、路径错误、超时等评测环境问题 | 否，不应进入有效比例 |

### 3.1.3 计算公式

设：

- \(N_C\)：GT 组件实例总数；
- \(S_C\)：`COMPILE_PASSED` 数量；
- \(M_C\)：`NOT_FOUND + AMBIGUOUS` 数量；
- \(F_C\)：`COMPILE_FAILED` 数量；
- \(E_C\)：`EVALUATOR_ERROR` 数量。

组件编译通过率：

\[
\mathrm{C\text{-}CPR}=\frac{S_C}{N_C}
\]

组件缺失或定位不确定率：

\[
\mathrm{C\text{-}MR}=\frac{M_C}{N_C}
\]

组件定位后编译失败率：

\[
\mathrm{C\text{-}CFR}=\frac{F_C}{N_C}
\]

当 \(N_C=0\) 或 \(E_C>0\) 时，三个比例均输出 `null`。当不存在评测器错误时，三个状态组互斥且完备，因此：

\[
\mathrm{C\text{-}CPR}+\mathrm{C\text{-}MR}+\mathrm{C\text{-}CFR}=1
\]

### 3.1.4 指标价值

- **C-CPR** 是组件层最低可用性的主指标，适合比较不同迁移方法能够产出多少可编译组件。
- **C-MR** 反映组件抽取、命名匹配、组件重组和检索能力问题；该值高时，优先检查判别器和目标文件组织。
- **C-CFR** 反映生成代码的语法、类型、import、props 或依赖问题；该值高而 C-MR 低时，说明组件大多能找到，但实现质量不足。

这三个指标联合使用可以区分“没有迁移出来”和“迁移出来但不能编译”，比只给一个成功率更有研究解释力。

## 3.2 单页面编译层

### 3.2.1 评价单位与判定

评价单位是 GT 中的页面。评测器优先使用清单中的目标文件提示定位页面入口；没有命中时，再按页面名称搜索同名 TS/TSX 文件。唯一定位后编译该页面入口及其依赖。

页面状态为：

- `PAGE_MISSING`；
- `PAGE_AMBIGUOUS`；
- `PAGE_COMPILE_FAILED`；
- `PAGE_COMPILE_PASSED`；
- `EVALUATOR_ERROR`。

### 3.2.2 计算公式

设：

- \(N_P\)：GT 页面总数；
- \(S_P\)：`PAGE_COMPILE_PASSED` 数量；
- \(M_P\)：`PAGE_MISSING + PAGE_AMBIGUOUS` 数量；
- \(F_P\)：`PAGE_COMPILE_FAILED` 数量；
- \(E_P\)：`EVALUATOR_ERROR` 数量。

页面编译通过率：

\[
\mathrm{P\text{-}CPR}=\frac{S_P}{N_P}
\]

当 \(N_P=0\) 或 \(E_P>0\) 时，P-CPR 输出 `null`。当前报告同时保存 \(M_P\) 和 \(F_P\) 的原始计数，用于区分页面缺失和页面编译失败；暂不额外命名两个比例，避免在页面数量很少时制造过多不稳定指标。如实验规模增大，可直接由固定分母计算页面缺失率 \(M_P/N_P\) 和页面编译失败率 \(F_P/N_P\)。

### 3.2.3 指标价值

组件可以分别编译，但页面组装仍可能因状态所有权、数据导入、Dialog props、布局容器或跨组件依赖而失败。P-CPR 验证的是“完整单页面入口能否形成可编译单元”，其验证深度高于单个组件，却仍不宣称页面能够正确交互或忠实显示。

## 3.3 多页面调用层

### 3.3.1 GT 调用图

原项目的页面导航、Dialog 打开、子页面依赖等关系被表示为有向边：

\[
e=(p_{source},p_{target},call\_type)
\]

每条 GT 边需要预注册一个独立测试入口。测试应至少验证：

- 源页面存在可触发入口；
- 目标页面、路由或 Dialog 能被调用；
- 必需 props、路由参数或事件接口有效；
- 适用时关闭、返回或回退接口能够工作。

### 3.3.2 状态分类

| 状态 | 含义 |
| --- | --- |
| `TEST_PASSED` | 源、目标页面可用且调用测试通过 |
| `TEST_FAILED` | 测试正常执行但断言失败 |
| `PAGE_UNAVAILABLE` | 关联页面缺失或未通过编译，调用测试无法成立 |
| `TEST_NOT_CONFIGURED` | GT 边尚未配置测试文件或命令 |
| `EVALUATOR_ERROR` | 测试文件丢失、运行器错误、超时等环境问题 |

### 3.3.3 计算公式

设：

- \(N_E\)：GT 调用边总数；
- \(T_E\)：已配置测试文件和测试命令的调用边数量；
- \(S_E\)：`TEST_PASSED` 数量；
- \(E_E\)：`EVALUATOR_ERROR` 数量。

调用测试覆盖率：

\[
\mathrm{Call\ Test\ Coverage}=\frac{T_E}{N_E}
\]

页面调用端到端通过率：

\[
\mathrm{PECTPR}=\frac{S_E}{N_E}
\]

PECTPR 使用所有 GT 边作为固定分母。`TEST_FAILED` 和 `PAGE_UNAVAILABLE` 都保留在分母中并视为未通过；缺少测试不能缩小分母。当 \(N_E=0\)、存在 `TEST_NOT_CONFIGURED` 或 \(E_E>0\) 时，PECTPR 输出 `null`。Call Test Coverage 仍单独报告，用于揭示测试准备是否完整。

### 3.3.4 指标价值

PECTPR 检验页面之间的接口集成，而不只是两个页面文件能否分别编译。它能够发现错误路由、Dialog props 不一致、事件未绑定、目标页面未挂载等跨页面问题。Call Test Coverage 则防止将“没有写测试”误解为“调用已经成功”。

## 3.4 工程层联合解释

| 典型结果 | 更可能的原因 | 优先检查方向 |
| --- | --- | --- |
| C-MR 高 | 组件未生成、重命名或判别器召回不足 | 组件清单、路径提示、定位证据 |
| C-CFR 高 | 组件实现存在类型或依赖错误 | import、props、MUI API、类型声明 |
| C-CPR 高而 P-CPR 低 | 单组件可用但页面组装失败 | 页面状态、数据、布局、根组件契约 |
| P-CPR 高而 PECTPR 低 | 单页面可用但跨页面接口失败 | 路由、Dialog、事件、参数和返回接口 |
| Coverage 低 | 评测准备不足 | 补齐并冻结 GT 边测试，不应下方法结论 |

## 4. 用户可见质量层

用户可见质量层使用人工提供的迁移前后截图对。图像 1 固定为原 WPF 页面，图像 2 固定为迁移后 React 页面。每个截图对必须描述同一页面的同一状态，例如默认状态、打开某个 Dialog 后的状态或显示同一组测试数据的状态。

截图评测是**静态视觉体验代理**，不是完整用户体验测量。它可以评价用户实际看到的页面结构和视觉表现，但不能直接证明交互正确、性能足够、键盘可达、屏幕阅读器可用或用户满意。

## 4.1 截图对可比较性

模型首先输出 `comparison_valid`：

- 任一截图损坏、主要区域不可见、明显不是同一页面或明显不是同一状态时，值为 `false`；
- 无效截图对的所有视觉分数必须为 `null`，并在 `validity_notes` 中说明原因；
- 可比较性不足属于样本问题，不应强制记为 0 分。

正式采集应尽量固定窗口或 viewport 尺寸、DPI/缩放、主题、字体、语言、测试数据、滚动位置、弹窗状态和时间相关内容。若截图尺寸不同，模型依据相对位置、比例和对齐进行判断，不直接比较像素坐标。

## 4.2 视觉分项指标

所有分项使用 0～100 分，并要求返回简洁理由与可见证据。

### 4.2.1 Component Fidelity：可见组件还原度

评价内容：

- 可见组件类型是否对应，例如按钮、输入框、表格、列表、图表和 Dialog；
- 组件数量是否缺失或重复；
- 父子层级、分组和显隐状态是否一致；
- 控件当前状态是否一致，例如选中、禁用、展开或空状态。

该指标比较功能角色，不要求 WPF 控件名和 MUI/React 组件名相同。截图无法观察到的隐藏组件不进入该截图状态的视觉判断。

价值：直接反映用户能否在迁移后页面看到与原页面相对应的操作和信息单元。

### 4.2.2 Layout Fidelity：页面布局还原度

评价内容：

- 元素相对位置和区域划分；
- 宽高比例、对齐方式和边距；
- 组件间距、分组关系和留白；
- 主次视觉层级和页面密度。

价值：组件即使全部存在，如果位置、尺寸和层次发生明显变化，用户仍会感知页面迁移失真。布局指标用于捕获这类“组件齐全但组织错误”的问题。

### 4.2.3 Style Fidelity：前端样式还原度

评价内容：

- 颜色与背景；
- 字体、字号、字重和文本样式；
- 边框、分隔线、圆角和阴影；
- 图标外观、按钮风格和控件视觉密度。

价值：衡量品牌感、视觉语义和局部呈现是否忠实，避免只关注结构而忽略用户最直观感受到的样式差异。

### 4.2.4 Content Fidelity：可见内容还原度

评价内容：

- 文本、标题、标签和提示信息；
- 数值、表格数据和列表内容；
- 图标表达的语义；
- 空状态、错误状态和当前数据状态。

价值：将“控件存在”与“控件展示了正确内容”分离。例如一个表格结构完全一致但字段、数值或标题错误时，组件分可以较高，内容分应下降。

### 4.2.5 Aesthetic Quality：目标页面视觉质量

该指标只评价迁移后 React 页面自身：

- 清晰度与可读性；
- 风格一致性；
- 视觉层次和平衡；
- 对齐、留白和整体完成度。

它不是忠实度指标。迁移后页面可能比原页面更现代、更美观，但同时偏离原页面；也可能高度忠实地还原一个视觉设计较旧的页面。为避免混淆，Aesthetic Quality 不进入 Overall Fidelity。

价值：补充回答“目标页面看起来是否成熟可用”，但只能作为静态视觉质量代理，不能替代真实用户研究。

## 4.3 视觉分数解释区间

以下区间用于提高模型和人工复核的一致性，不把连续分数机械转换为成败：

| 分数 | 忠实度维度解释 | 美观度解释 |
| --- | --- | --- |
| 90～100 | 可见范围内几乎无差异，仅有轻微细节偏差 | 完成度高，几乎没有明显视觉问题 |
| 75～89 | 主体一致，存在少量但可辨认差异 | 整体良好，存在局部一致性或精细度问题 |
| 60～74 | 核心结构保留，但多个局部差异明显 | 基本可接受，但层次、密度或细节仍较粗糙 |
| 40～59 | 主要结构或视觉语义有显著偏离 | 视觉质量一般，存在明显影响阅读或一致性的问题 |
| 0～39 | 大量缺失、错位或风格完全不同 | 视觉完成度低，严重影响理解或使用感受 |

## 4.4 Overall Fidelity 计算

设单个有效截图对的分项分数为：

- \(C_v\)：Component Fidelity；
- \(L_v\)：Layout Fidelity；
- \(S_v\)：Style Fidelity；
- \(T_v\)：Content Fidelity。

程序使用冻结权重计算总忠实度：

\[
\mathrm{Overall\ Fidelity}
=0.35C_v+0.30L_v+0.20S_v+0.15T_v
\]

权重之和为 1。当前权重体现以下优先级：

1. 可见组件是否完整是页面能否被识别和使用的基础；
2. 布局决定组件之间的空间与层次关系；
3. 样式影响视觉忠实，但通常不应压过结构缺失；
4. 内容状态重要，但人工截图可能使用不同动态数据，因此权重略低并要求尽量固定测试数据。

总分由程序确定性计算，而不是让 LLM 再凭总体印象给分。更换权重会改变研究问题和方法排序，因此正式实验冻结后不得按结果调权；如需讨论权重影响，应作为独立敏感性分析报告。

## 4.5 覆盖率与聚合

设：

- \(N_V\)：登记的 GT 截图对总数；
- \(S_V\)：状态为 `EVALUATED` 的有效截图对数；
- \(I_V\)：`INVALID_COMPARISON` 数量；
- \(E_V\)：`EVALUATOR_ERROR` 数量。

视觉截图对覆盖率：

\[
\mathrm{Visual\ Pair\ Coverage}=\frac{S_V}{N_V}
\]

当前实现只对 `EVALUATED` 截图对的分项分数、Overall Fidelity、美观度和 confidence 计算算术平均。无效截图和评测器错误不按 0 分进入均值，而由 Coverage、\(I_V\) 和 \(E_V\) 单独揭示。

若一个页面有多个状态，直接对所有截图对做宏平均会使状态较多的页面获得更大权重。正式研究推荐同时报告：

1. **截图对宏平均**：当前实现直接输出，适合描述所有已评状态的平均质量；
2. **页面宏平均**：先对同一页面的有效状态求平均，再对页面求平均；
3. **项目宏平均**：多项目实验中，先求页面平均，再对项目求平均。

逐截图对 JSONL 已保留完成后两种聚合所需的数据。

## 4.6 置信度与问题严重度

`confidence` 范围为 0～1，表示模型对截图可比较性和证据充分性的信心，不是质量分数。低 confidence 的截图应优先进入人工复核。

每个视觉问题使用以下严重度：

| 严重度 | 判定建议 |
| --- | --- |
| `CRITICAL` | 核心组件缺失、主要区域错位或内容错误，足以改变页面用途或阻碍主要任务 |
| `MAJOR` | 明显影响布局、信息层级或视觉一致性，但核心任务仍可辨认 |
| `MINOR` | 局部颜色、间距、字体或装饰细节差异，不改变核心结构与任务 |

问题同时记录 `category`、原图证据、目标图证据和改进建议，以支持失败归因和后续人工复核。

## 5. 两层指标的联合价值

两层指标共同形成从代码到用户可见结果的验证链：

| 工程结果 | 视觉结果 | 可支持的结论 |
| --- | --- | --- |
| 编译失败 | 不评分或仅作案例观察 | 迁移尚未达到最低工程可用性 |
| 编译通过 | 忠实度低 | 代码有效，但页面结构或呈现偏离原实现 |
| 编译通过 | 忠实度高、美观度低 | 迁移忠实，但目标页面自身视觉完成度不足 |
| 编译通过 | 忠实度低、美观度高 | 发生了较成功的重新设计，但不能称为忠实迁移 |
| 编译与调用通过 | 忠实度高 | 同时具备较强工程可用性和静态视觉还原证据 |

即使最后一行成立，也只能说明已覆盖状态下的编译、调用和静态视觉表现良好，不能自动推出业务语义完全一致或真实用户体验相同。

## 6. 推荐报告方式

每个迁移方法至少报告：

| 组别 | 必报内容 |
| --- | --- |
| 组件 | C-CPR、C-MR、C-CFR、各状态计数 |
| 页面 | P-CPR、页面缺失/歧义计数、页面编译失败计数 |
| 调用 | PECTPR、Call Test Coverage、各调用状态计数 |
| 视觉忠实度 | Component、Layout、Style、Content、Overall Fidelity |
| 视觉质量 | Aesthetic Quality，必须与忠实度分开 |
| 样本质量 | Visual Pair Coverage、INVALID_COMPARISON、EVALUATOR_ERROR |
| 可复现信息 | 项目、方法、run、模型、prompt 版本、截图哈希、清单版本 |

对生成式迁移方法应运行多个预先确定的 run，报告均值和离散程度，不挑选最佳一次。视觉 LLM Judge 应固定模型档位、提示词版本、温度、输入顺序和截图清单，并在一部分盲法人工样本上检查人与人、人与模型的一致性。

## 8. 当前边界

- “找到并编译”只代表编译层最低可用性，不代表组件行为、数据语义或视觉完全正确；
- 页面调用测试只覆盖冻结 GT 边和测试中明确断言的接口；
- 截图只能评价可见静态状态，不能观察隐藏状态、完整交互路径和动态行为；
- LLM 视觉评分存在模型偏差与非确定性，不应成为唯一视觉证据；
- 不同分辨率、字体渲染、操作系统主题和动态数据都可能影响视觉分数；
- 任何 `null` 主指标都表示当前证据不足或评测器异常，不能按 0 分或 100 分处理。

这些边界不是取消分层评价的理由，而是规定每个指标能够支持的结论范围。工程层提供可执行的最低保证，视觉层提供用户可见质量证据，后续若增加浏览器交互、可访问性、任务完成率或真实用户研究，应继续作为新的独立层级加入，而不是重定义现有指标。
