## 摘要

大量桌面应用采用 WPF、XAML 和 MVVM 架构构建。在应用向 Web 平台演化的过程中，WPF 到 React 的迁移不仅涉及标签和语法转换，还需要处理布局系统、数据绑定、事件命令、资源字典、组件依赖和目标组件库 API 等跨框架语义差异。基于规则的迁移方法具有确定性，但难以覆盖复杂上下文；直接使用大语言模型具有较强生成能力，却容易产生依赖顺序错误、MUI API 幻觉和行为不一致。针对这些问题，本文提出一种三阶段的知识增强与依赖驱动前端UI迁移方法 MigraUI。阶段1由页面布局解析器、数据类解析器和资源依赖解析器组成。对单页面，页面布局解析器直接依据 XAML 嵌套深度构造以组件实例为节点的组件依赖树；布局包含关系天然为树，不把事件、数据、模板或资源引用混入父子边。对页面导航以及数据、资源、样式和模板引用，系统统一采用“主结构 + 额外依赖边”表示：规则分析先选择可稳定迁移的主关系，把闭环边和非主关系单独记录；规则无法解析的动态引用才由 LLM 辅助分类。阶段2单独建模最小迁移单元“组件”：对 WPF 标准组件执行规则映射，对 WPF 自定义组件先由 LLM 总结当前代码段中的功能，再经向量相似度检索定位候选 MUI 组件，最后把 WPF 组件代码与 MUI 知识证据输入 LLM 生成 React 组件。阶段2重点说明 RAG 知识库、检索和单组件生成方法，不规定组件树调度顺序，也不代表真实执行时的完整输入。阶段3先独立迁移静态资源和 C# 核心数据类，再按主结构迁移页面组件和主要导航，最后按依赖类型恢复、重写或阻塞额外依赖边，形成统一的“规则解析—先拆迁移—后合引用—工具验证”流程。端到端实验比较传统规则适配、预算匹配的纯LLM和完整方法，并通过六个核心消融分离RAG、组件拆分、自底向上顺序、子节点代码、依赖编排与工具反馈的贡献；统一只读评测器自动计算页面构建/渲染、架构无关组件实例复刻、导航边、成对截图与成本指标，局部视觉、VLM和人工评价仅作补充。

**关键词：** 遗留系统迁移；WPF；React；Material UI；Agentic RAG；依赖树；多Agent系统

## 1 引言

WPF 应用通常以 XAML 描述界面，以 C# ViewModel 和命令系统承载状态与交互；React则以函数组件、单向数据流和Web平台机制组织界面[E029][E071]。两者虽然都支持声明式UI，但运行环境、组件生命周期、数据流和样式机制存在明显差异。因此，迁移不能被简化为 XAML 标签到 JSX 标签的一一替换。

一个真实 WPF 页面可能引用用户控件、资源字典、值转换器、DTO、服务接口和父级 DataContext。若目标 React 页面在依赖尚未迁移时生成，大模型只能猜测子组件接口，容易产生不存在的 props 或错误 import。即使所有依赖可用，MUI 的组件选择、props、组合方式和版本约束也不一定能被通用模型准确回忆，导致生成代码表面合理但无法编译或偏离目标实现。

现有方案大致分为两类。规则化和模型驱动方案通过逆向恢复、元模型、映射与模板确定性地处理界面结构[E013][E014][E015][E018]；近年的生成式方案开始引入LLM或Agent处理跨框架语义，但仍需规则修复或工具验证[E007][E008][E010][E009]。本文采用混合路线：确定性分析负责仓库结构、依赖和可直接映射的语法；知识检索负责提供目标组件契约；大模型负责上下文相关的语义重构；编译器和测试工具负责发现错误并形成反馈。

本文拟回答以下研究问题：

- **RQ1：** 由“依赖抽取—单组件迁移原语—完整迁移流程编排”构成的三阶段方法，能否提高 WPF→React/MUI 迁移的编译正确性、API有效性和语义质量？
- **RQ2：** 对单个 WPF 组件，“标准组件规则映射 + 自定义组件功能总结与 MUI 向量检索 + LLM生成”的组件迁移方法，能否准确定位目标组件并提高 React 组件的 API 有效性与语义质量？
- **RQ3：** 在真实流程中，规则优先地将页面、数据、资源、样式和模板关系拆为主结构与额外依赖边，再执行“先拆迁移—后合引用”，能否在保持组件树自底向上顺序的同时减少未解决引用、接口猜测和重复生成？
- **RQ4：** 将当前节点的所有直接子节点迁移后代码作为额外上下文，并在根节点完成后融合资源、数据和样式依赖进行页面整合，能否改善单页面的结构一致性、编译正确性和交互完整性？
- **RQ5：** 在所有单页面迁移完成后，先沿主页面依赖树自底向上修改主导航逻辑，再补齐单独记录的返回边和交叉导航边，能否提高多页面联动一致性？
- **RQ6：** 由“构建可行性—组件/页面关系正确性—视觉与人工语义一致性”构成的分层门控评测，能否在可控自动化成本下比单一编译通过率更准确地反映迁移质量？截图自动指标与视觉语言模型裁判（VLM-as-a-Judge）在其中应分别承担何种作用？

本文的预期贡献如下：

1. 提出一种“依赖抽取—单组件迁移原语—完整迁移流程编排”三阶段 Pipeline，在阶段1以页面布局、数据类和资源依赖三类 Parser 产出逐页面组件依赖树、各类主依赖结构、统一额外依赖边表和资源依赖映射表，显式化 WPF 工程级上下文；
2. 提出一种面向最小迁移单元的 MUI RAG 组件迁移方法，对标准组件使用规则映射，对自定义组件通过 LLM 功能总结和向量相似度检索定位候选 MUI 组件，再以 LLM 生成 React 实现；
3. 提出一种将阶段2组件迁移原语编排为完整工程流程的顺序性方法：以“规则解析—先拆迁移—后合引用—工具验证”统一处理数据、资源、样式、模板和页面导航中的循环；先迁移静态资源与核心数据类，再沿组件层级树自底向上注入直接子节点迁移代码，最后整合页面与额外依赖边；
4. 建立面向不同输出架构的统一自动评测框架：以RuleTrans-MUI、LLM-Direct-Budget、MigraUI-NoRAG三条baseline和完整MigraUI为端到端对比方法，通过隐藏evaluation manifest和同一评测器计算P-CPR/P-RPR/PBPR、CIRR、Nav-F1/NTPR、SPC+SSIM/CLIP及成本；组件内部、局部视觉、VLM与人工指标只作机制诊断或小型校准。

## 2 背景与问题分析

### 2.1 WPF与React的范式差异

| 维度 | WPF | React | 迁移问题 |
|---|---|---|---|
| UI描述 | XAML | JSX/TSX | 标签可转换，但属性语义不完全对应 |
| 数据流 | Binding/DataContext，可双向绑定 | props/state，单向数据流 | 隐式继承需改为显式状态和事件 |
| 事件 | RoutedEvent、ICommand | DOM/合成事件、回调函数 | 命令参数和冒泡机制需重构 |
| 布局 | Grid、StackPanel、DockPanel | CSS Grid/Flexbox | 尺寸、对齐和自适应行为不同 |
| 样式 | ResourceDictionary、Style、Trigger | CSS/Theme/条件渲染 | 资源继承和触发器需显式实现 |
| 生命周期 | Loaded/Unloaded、属性通知 | useEffect和状态更新 | 清理、依赖数组和闭包风险 |
| 组件生态 | WPF控件及项目自定义控件 | React + MUI | 组件名和props通常非一一映射 |

### 2.2 直接规则迁移的局限

规则适合处理 `TextBox.Text` 到受控组件 `value/onChange`、`StackPanel` 到 Flex布局等确定性模式，但对 DataTemplateSelector、多层 Binding、资源覆盖、动态主题和复杂命令链需要理解上下文。试图穷举全部规则会导致维护成本随项目特性快速增长。

### 2.3 直接LLM迁移的局限

大模型可以根据页面语义进行重构，但面临四类风险：

- 不能稳定遵循 MUI 的真实API、版本和组合约束，生成不存在或已废弃的组件属性；
- 不知道其他页面和组件的迁移状态，猜测 import 和接口；
- 对大型页面一次性重写，局部修复可能破坏已正确区域；
- 编译成功后缺乏对布局和交互等价性的进一步验证。

### 2.4 知识增强迁移

检索增强生成（Retrieval-Augmented Generation, RAG）通过显式检索外部知识约束生成[E024]；在代码任务中，DocPrompting和RepoCoder分别展示了文档检索与仓库级迭代检索对生成的作用[E023][E035]。UI迁移的检索目标不是孤立文本片段，而是“可直接用于生成的目标组件及其完整契约”。因此，检索结果应从 chunk级证据聚合为组件级候选，再回填组件的完整文档和示例。

## 3 任务定义与研究范围

给定 WPF 项目 \(P_s\)、目标 React 工程骨架 \(P_t\) 和目标组件知识库 \(K\)，系统需要生成迁移结果 \(M(P_s,K)=P_t'\)。对每个源页面 \(p\)，输出至少包括：

- React函数组件或页面；
- TypeScript props/state类型；
- 样式文件或主题映射；
- 对已迁移子组件和服务适配层的引用；
- 可追溯的源文件、知识来源和验证记录。

本文重点迁移：

- XAML界面树和自定义组件引用；
- 常见布局、样式和资源；
- 数据显示、表单状态和事件命令适配；
- 与页面直接相关的轻量ViewModel状态。

本文不自动重写高风险核心业务逻辑。复杂业务逻辑通过服务接口、API适配层或待人工处理标记与前端UI解耦。该范围限制有助于使“UI迁移正确性”具有清晰边界。

## 4 MigraUI方法

### 4.1 总体架构

```text
WPF仓库
  → 阶段1：依赖抽取
       页面布局Parser（XAML布局/组件）
       + 数据类Parser（C#核心数据类）
       + 资源依赖Parser（页面/组件/模板/数据/样式依赖）
       → 逐页面组件依赖树 + 各类主依赖结构 + 统一额外依赖边表 + 资源依赖映射表
  → 阶段2：单组件迁移方法（最小迁移单元）
       标准组件规则映射
       + 自定义组件功能总结/MUI向量检索
       + WPF代码/MUI知识增强LLM生成
  → 阶段3：完整迁移流程与顺序编排（核心）
       数据/资源/样式/模板：先拆迁移 → 后合额外引用 → 验证
       → 单页面：按组件层级深度自底向上调用阶段2原语
          当前WPF代码 + MUI候选 + 直接子节点迁移后代码
       → 根节点 + 资源/数据/样式依赖 → 完整页面
       → 全部单页完成后，按主页面依赖树自底向上联调
       → 补齐额外返回边/交叉导航边
  → 公共保障：规则预转换 + 多路检索 + 工具验证 + 局部修复
  → React工程与迁移审计记录
```

#### 4.1.1 三阶段边界

阶段1只负责把 WPF 工程中隐式的页面、组件、模板、数据和样式关系显式化，不生成最终 React 代码。阶段2定义“单个组件如何迁移”的可复用原语，重点是目标 MUI 组件定位、RAG 知识组织和 LLM 生成；为了集中展开 RAG，该阶段有意不讨论它在组件树中的调用顺序，也不把“已迁移子节点代码”写成阶段2原语的必备输入。阶段3才定义真实的端到端迁移过程：先迁移静态资源和核心数据类，再将阶段2原语按单页面组件层级树自底向上编排，运行时注入所有直接子节点的迁移后代码，然后整合完整页面。全部单页面完成后，先按主页面依赖树处理主从导航，再读取额外页面依赖边补齐返回和交叉跳转。这一“能力定义与顺序编排分离”以及“主树调度与额外边补全分离”是理解阶段2–3关系的关键。

### 4.2 阶段1：依赖抽取

阶段1不负责生成 React/MUI 代码，而是由三类 Parser 将 WPF 的页面结构、核心数据结构和跨文件依赖转换为统一中间表示。三个 Parser 的输出以文件路径、命名空间、类名、`x:Class`、资源键和源码位置等稳定标识对齐，再由资源依赖解析器组装为类型化依赖图 \(G=(V,E,\tau)\)。

#### 4.2.1 页面布局解析器（Page Layout Parser）

页面布局解析器识别并解析 `.xaml` 文件，重建 WPF 界面的层次结构，其职责包括：

- 识别 `Window`、`Page`、`UserControl` 等页面或组件根节点，建立 XAML 文件与 `x:Class` 代码类的关联；
- 解析 `Grid`、`StackPanel`、`DockPanel`、`Canvas` 等布局容器、行列定义、嵌套层级、排列顺序与主要布局属性；
- 识别 WPF 内置控件、项目自定义控件及它们的属性、事件、内容与父子包含关系；
- 保留 `Binding`、`StaticResource`、`DynamicResource`、`TemplateBinding` 等引用点及其源位置，但不在本 Parser 内负责跨文件依赖求解。

该 Parser 输出页面布局中间表示（Layout IR）和组件实例清单。Layout IR 至少保存节点类型、属性、父子关系、源码范围、绑定引用和资源引用，作为组件依赖解析和阶段2组件迁移的结构基础。

#### 4.2.2 数据类解析器（Data Class Parser）

数据类解析器识别并解析 `.cs` 文件，获取与 UI 直接相关的核心数据类定义。它不以扫描全部业务实现为目标，而是以 XAML 的 `x:Class`、`DataContext`、Binding 路径、自定义控件类型和 code-behind 引用作为入口，定位页面和组件实际使用的数据结构。主要抽取：

- 类、记录、结构体和枚举的全限定名称、继承/接口关系与源文件；
- 属性和与 UI 相关的公开字段，包括类型、可空性、集合元素类型、可见性和默认值；
- 数据类之间的嵌套、聚合和集合引用，以及 Binding 路径所对应的成员链；
- 用于页面与组件接口推导的必要类型信息，但不自动迁移数据库、权限、网络访问等核心业务逻辑。

该 Parser 输出数据类中间表示（Data IR），供资源依赖解析器建立数据依赖。阶段2可读取其中与当前组件相关的源侧类型事实；正式的 C#→TypeScript 数据类迁移、可复用类型产物和后续 props/state 数据契约由阶段3按流程生成。

#### 4.2.3 资源依赖解析器（Resource Dependency Parser）

资源依赖解析器综合 Layout IR、Data IR、ResourceDictionary、code-behind 和项目级文件，统一解析以下五类依赖：

1. **页面依赖。** 分析页面引用、导航、页面容器嵌套、共享组件、共享数据与共享资源形成的多页面关系。系统从主页面或入口页面出发选择主导航边构造页面依赖树，并把返回、重复访问、跨分支跳转和多父导航保存为额外页面依赖边，供阶段3分两步完成多页面联动。
2. **组件依赖。** 对每个页面的 Layout IR 按 XAML 包含关系和嵌套深度构造逐页面组件依赖树。树节点表示组件实例，父子边只表示直接布局包含；事件、命令、数据、模板和资源引用作为节点属性或其他类型依赖保存，不混入组件树父子边。跨页面复用的自定义组件使用统一类型标识，但其在各页面中的实例仍分别处于对应布局树位置。
3. **模板依赖。** 解析 `ControlTemplate`、`DataTemplate`、`ItemsPanelTemplate`、`TemplateBinding` 及模板选择器之间的定义—引用关系，保留模板嵌套、目标类型和使用位置。
4. **数据依赖。** 将 `DataContext`、Binding 路径、`ItemsSource`、命令参数和组件数据输入对齐到 Data IR 中的核心数据类及其成员，形成页面/组件到数据类的可追溯依赖。
5. **样式依赖。** 解析 `Style`、`BasedOn`、`StaticResource`、`DynamicResource`、`MergedDictionaries`、Trigger 和主题资源的定义、作用域、覆盖顺序与引用关系。

资源依赖解析器的统一节点类型包括 `Page`、`Component`、`Template`、`DataClass`、`Style/Resource` 和必要的 `Converter/Command`；边必须标记依赖类型、抽取来源、源码位置和解析状态。该 Parser 最终输出：

- **页面依赖树与统一额外依赖边表**：页面依赖树表示从主页面出发的主要导航/包含层级；页面返回/交叉/多父边，以及数据、资源、样式和模板的闭环边统一另表保存，不因构造主结构而丢弃；
- **逐页面组件依赖树**：表示每个页面内组件的组合与引用层级，并保留跨页面共享组件标识；
- **资源依赖映射表**：统一记录模板、数据和样式资源的定义、引用、作用域、覆盖关系与未解析项。阶段1只保存 WPF 源侧事实；阶段2只定位组件层面的 MUI 候选，静态资源的 MUI theme token、CSS、文件路径或组件组合目标映射统一在阶段3的静态资源迁移中生成。

#### 4.2.4 三类Parser组装与依赖树生成

页面布局解析器与数据类解析器可并行产生 Layout IR 和 Data IR，资源依赖解析器在两类 IR 基础上进行跨文件求解。对无法解析的动态资源、反射引用、运行时导航或动态 `DataContext`，系统必须保留未解析引用和原始证据，不得默认为无依赖。

组件与页面采用两种不同的简单调度表示。逐页面组件依赖树直接来自 XAML 语法树的布局包含关系：每个组件实例只有一个直接布局父节点，因此可按深度稳定地自底向上迁移。共享组件类型、事件、数据、模板和资源引用不会改变实例的布局父节点，统一在节点属性、共享类型表和资源依赖映射表中保存。

页面导航本质上可能是有向图。为复用现有页面树流程，系统从显式主页面、启动窗口或入口路由出发遍历导航关系；首次使页面可达的边选为主导航边，构成页面依赖树。若一个页面存在多个候选父页面，优先选择显式容器/所有者关系，其次选择距入口更近的导航边，仍并列时按稳定源码顺序确定，并记录 `primary_parent_reason`。指向已访问页面、祖先页面或其他分支页面的边不参与树结构，而记录在额外页面依赖边表中，并标注 `return`、`back`、`cross`、`secondary_parent` 或 `unresolved_dynamic` 等类型。若存在多个入口，则构造页面依赖森林或增加不生成代码的虚拟根节点。

#### 4.2.5 组件与页面“循环”的边界

在本文定义下，单页面组件依赖树描述的是具体组件实例的布局包含层级，而不是所有引用关系的混合图，因此树内不会出现循环。所谓“组件循环”通常来自自定义组件类型相互引用、事件回调、共享状态或模板/资源关系；这些关系由资源依赖解析器单独记录，不改变按 XAML 深度构造的迁移顺序。若某自定义组件类型在静态展开路径上直接或间接无条件实例化自身，系统将其标记为 `recursive_component_ref` 异常并转人工确认，而不为少量异常改变主流程。

页面层面的 A→B→A 则是常见导航往返。系统把 A→B 作为主页面依赖树中的父子边，把 B→A 作为额外返回边保存。对于 A→C→B 等跨分支跳转或一个页面具有多个入口的情况，同样选择一个确定的主父节点用于调度，其余关系保存为交叉边或次父边。该表示不宣称原始页面导航关系本身是树，只是以“主树 + 额外边”复用简单稳定的自底向上流程。

#### 4.2.6 统一循环依赖处理：主结构、额外边与先拆后合

数据类、资源、样式和模板关系也可能闭环。为避免为每种依赖建立完全不同的复杂算法，系统复用页面依赖的“主结构 + 额外边”思想，并统一执行四步：

1. **规则解析。** 依据类名/命名空间、字段类型、资源键、作用域、声明顺序、`MergedDictionaries`、`BasedOn`、`StaticResource`、`DynamicResource`、模板键和引用位置建立确定性依赖边；使用深度优先遍历的访问状态识别闭环边。动态键、反射、模板选择器或字符串间接引用无法确定时才进入 LLM 辅助分析。
2. **先拆迁移。** 暂不恢复闭环边，先按声明、包含、作用域和确定性主依赖顺序迁移各个节点；需要互相引用的目标先生成名称、类型声明、资源键或占位接口，避免迁移单元相互等待。
3. **后合引用。** 两端节点完成后，根据依赖类型恢复类型引用、资源键、样式继承或模板引用；若原循环不能在目标框架中合法保留，则按确定性规则提取共享基础项或显式阻塞，而不是任意删除边。
4. **工具验证。** 重新执行 TypeScript、import、资源键唯一性、样式继承、模板展开、渲染和交互检查；失败时进行局部修复，超过上限或语义仍不明确时转人工。

统一额外依赖边至少记录：`source_id`、`target_id`、`dependency_type`、`source_location`、`cycle_closing`、`resolution_strategy`、`analysis_source`（`rule|llm`）、`confidence` 和 `status`。不同类型只替换“后合引用”的规则：

| 依赖类型 | 典型循环 | 先拆 | 后合 |
|---|---|---|---|
| 数据类 | `Order`引用`Customer`，`Customer`又引用`Order` | 先生成全部命名类型及非闭环字段；优先放入共享类型模块 | 恢复闭环字段类型，跨文件时使用 `import type`；禁止生成递归默认实例 |
| 资源字典/资源键 | 字典互相合并，或资源键跨字典回引 | 先迁移文件、键和值本体，按作用域/声明顺序确定主导入关系 | 目标侧可安全引用时恢复额外键引用；若合并顺序或覆盖语义冲突则阻塞 |
| 样式 | `Style.BasedOn`形成回路 | 分别迁移各样式自身 setters、trigger摘要和目标token | 规则可证明无冲突时提取共同基础样式/token并重连；否则视为无效或歧义依赖转人工 |
| 模板 | 模板相互引用或递归展开 | 分别迁移模板主体和参数/资源接口，闭环引用保留占位 | 非递归组合可在节点完成后恢复；可能无限展开的结构递归不自动合并，标记阻塞 |
| 页面导航 | A→B→A或跨分支跳转 | 先沿主页面依赖树处理主要导航 | 恢复返回、交叉和次父边，并执行页面组联调 |

LLM只作为规则分析的补充。其输入包含源码片段、已解析符号、邻接关系和规则失败原因，输出候选目标、依赖语义、建议策略、证据和置信度；LLM不得直接删除闭环边或把低置信猜测写入主结构。高置信结果仍须通过解析/编译/渲染验证，低置信结果保留为 `unresolved` 并转人工。

### 4.3 阶段2：基于MUI RAG的单组件迁移方法

阶段2将“组件”定义为 UI 迁移的最小生成单元，集中回答一个问题：给定当前 WPF 组件代码，如何定位可能使用的 MUI 标准组件，并在目标 API 知识约束下生成 React/TypeScript 组件。由于 MUI 知识库构建、多路检索、组件候选聚合和上下文回填内容较多，本文将其独立为一个阶段详细展开。

阶段2描述的是可被阶段3重复调用的“组件迁移原语”，而非端到端迁移流程。它不在本阶段中决定组件树的调度顺序，也不将已迁移子组件代码视为最小原语的固定输入。自底向上调度、直接子节点代码注入、资源/数据依赖整合及页面级验证统一在阶段3定义。

#### 4.3.1 当前组件拆解与目标组件定位

阶段2的输入是一个已由阶段1定位的 WPF 组件或局部 UI 子树。系统保留当前节点的 XAML、相关 code-behind/ViewModel 摘要、Binding 与资源引用，并区分两类目标定位路径：

1. **WPF标准组件。** 使用可审计规则将 `Button`、`TextBox`、`ComboBox`、`DataGrid` 等常见控件映射到候选 MUI 标准组件或明确的 React/CSS 布局骨架。规则只给出候选目标和确定性属性转换，不代替后续 LLM 对上下文、状态和交互的重构。
2. **WPF自定义组件。** 先由 LLM 对当前代码段中该组件的展示目的、数据输入、主要交互和布局角色生成语言无关的功能摘要；再以功能摘要和必要代码特征检索 MUI 知识库，按向量相似度定位可能的 MUI 标准组件或组件组合。

标准组件规则映射和自定义组件语义检索两条路径最终均输出带来源、版本、得分和适用证据的 MUI 候选集，而不是直接将首个检索结果当作确定映射。

##### 4.3.1.1 确定性规则预转换

确定性映射在LLM调用前完成，以减少生成空间：

| WPF构造 | React目标 | 处理方式 |
|---|---|---|
| `Binding Mode=TwoWay` | `value` + `onChange` | 生成受控状态骨架 |
| `Binding Mode=OneWay` | 只读props/state | 直接映射 |
| `StackPanel` | Flex布局 | 根据Orientation生成样式 |
| `Grid` | CSS Grid | 转换行列定义和定位属性 |
| `StaticResource` | 资源引用占位或已迁移目标资源 | 阶段2保留引用语义；真实执行时由阶段3注入静态资源迁移结果 |
| `DynamicResource` | 动态资源引用占位 | 阶段2保留动态性约束；阶段3结合主题/CSS变量迁移结果完成绑定 |
| `ICommand` | 事件回调 | 保留命令名和参数语义 |
| `ItemsControl` | `map` + `key` | 生成列表结构和key占位 |

无法确定性转换的节点保留原始结构、绑定信息和转换提示，交给知识增强生成模块处理。

#### 4.3.2 MUI知识库

##### 4.3.2.1 文档规范化

MUI 文档、TypeScript 类型声明和官方代码示例首先被整理为统一结构：组件名、类别、版本、import路径、props契约、事件、约束、代码示例和常见错误。每条知识均绑定唯一 `component_id`，避免同名组件或版本混淆。

##### 4.3.2.2 双类型切分

- **文本chunk**：功能说明、props解释、使用限制和设计规范；
- **代码chunk**：完整TSX示例、组合用法和事件处理片段。

文本chunk使用文本嵌入模型，代码chunk使用代码嵌入模型。两者同时建立BM25倒排索引，保留组件名、prop名和事件名的精确匹配能力[E090]。

##### 4.3.2.3 元数据

每个chunk至少包含：

```json
{
  "component_id": "唯一组件标识",
  "component_name": "组件名",
  "chunk_type": "text|code",
  "category": "layout|input|display|feedback|navigation",
  "source": "文档或源码位置"
}
```

#### 4.3.3 三路检索与组件级聚合

对待迁移的 WPF 子树生成三类查询：

1. **代码密集检索**：源XAML/规则预转换骨架 → BGE-Code-v1 → 代码示例索引；
2. **文本密集检索**：LLM或规则生成的语言无关功能描述 → BGE-M3 → 文本文档索引；
3. **稀疏检索**：控件名、属性名、事件名和领域关键词 → BM25。

三路返回的chunk先在各自路径内归一化，再按 `component_id` 聚合：

\[
Score(c)=\sum_{p\in\{code,text,bm25\}}w_p\max_{k\in R_p,comp(k)=c}\tilde{s}_p(k)
+\lambda\frac{cover(c)}{3}
\]

其中，`max` 防止文档较长、chunk较多的组件通过数量优势抬高得分，`cover(c)` 奖励被多路共同召回的组件。权重、覆盖奖励和截断阈值只在验证集上调整。

组件按得分归一化后执行动态核截断：选择累计概率达到 \(P\) 的最小组件集合，同时以 \(K_{max}\) 限制上下文规模。系统随后回填这些组件的完整API契约、关键示例和版本信息，而不是只把命中的零散chunk交给生成模型。

#### 4.3.4 组件代码生成

生成prompt包含：

- 当前单个组件的 XAML 和必要的 code-behind/ViewModel 摘要；
- 规则预转换结果；
- 标准组件规则映射或自定义组件功能摘要；
- 检索到的候选 MUI 组件及其完整知识；
- 全局约束：TypeScript、Hooks规则、受控组件、列表key、可访问性和禁止API；
- 输出schema：组件代码、类型、样式、依赖和未解决事项。

生成模型将 WPF 组件代码与可能使用的 MUI 标准组件共同作为输入，输出候选 React/TypeScript 组件。阶段2对该候选执行组件级 TypeScript/API/静态检查，但此时只评价单个组件迁移原语的能力，不宣称已恢复完整页面上下文。

#### 4.3.5 阶段2的能力边界：组件迁移原语并非完整流程

阶段2的独立输入契约可记为：

\[
PrimitiveInput(v)=\langle WPFCode_v, LocalContext_v, MUICandidates_v, Constraints\rangle
\]

其输出为当前节点的候选 React 组件、类型/样式与未解决依赖。真实执行时，阶段3将该原语扩展为：

\[
RuntimeInput(v)=PrimitiveInput(v)\cup\{MigratedCode(u)\mid u\in Child(v)\}
\]

即向当前节点注入其所有直接子节点的迁移后代码及真实接口。因此，阶段2不能被单独写成“完整的自底向上组件迁移系统”；自底向上的顺序性及完整输入/输出契约属于阶段3。

### 4.4 阶段3：完整迁移流程与顺序编排

阶段3是负责工程级迁移顺序的核心阶段。它不重复定义 RAG 如何检索单个组件，而是把阶段2的组件迁移原语、阶段1的依赖产物和各类迁移结果组织为可执行的端到端流程。总体顺序为：

```text
阶段1依赖分析结果
  → 静态资源迁移
  → C#核心数据类迁移到TypeScript
  → 对每个单页面：
       按组件层级深度自底向上迁移所有组件
       → 以根节点迁移代码为基础整合完整页面
  → 所有单页面完成
  → 按主页面依赖树自底向上修改主导航逻辑
  → 根据额外页面依赖边补齐返回/交叉跳转
  → 多页面联调完成
```

#### 4.4.1 静态资源迁移

静态资源迁移在页面代码生成之前执行，处理图片、图标、字体、颜色、尺寸、样式、主题和模板等可独立于页面代码处理的资产。系统以阶段1的资源依赖映射表为输入，对源文件进行复制、格式/路径调整和去重，并将 WPF 样式资源转换为可供 React/MUI 使用的 theme token、CSS 或显式样式配置。执行时先迁移资源文件、资源键、样式自身内容和模板主体，再读取统一额外依赖边表恢复可合法表达的跨资源引用；`BasedOn`循环优先通过提取共同基础样式/token重写，模板递归展开或资源覆盖顺序无法确定时则阻塞。对 `DynamicResource`、Trigger、`ControlTemplate` 等无法机械转换的项，保留来源证据和未解决状态，在页面整合时进一步处理。

输出包括目标资源文件、MUI theme/CSS 映射、新路径、主依赖关系、已恢复额外边和未解决资源。以确定性资源依赖为主顺序，被引用资源先于引用方迁移；无法解析或源语义冲突的资源关系保留证据并进入人工处理，不影响组件层级树的主调度。

#### 4.4.2 核心数据类迁移

数据类迁移以阶段1的 Data IR、数据主依赖和额外依赖边为输入，将与 UI 直接相关的 C# 核心数据类转换为 TypeScript `interface`、`type`、`enum` 或必要的轻量类。类型迁移需要保留成员名称、可空性、集合元素类型、嵌套/继承关系和 Binding 成员链；不在此步迁移数据库、权限、网络访问等核心业务逻辑。

数据循环同样采用先拆后合：第一遍生成全部命名类型、枚举和非闭环字段，使各类型标识先存在；第二遍恢复额外边中的相互引用字段。相互引用的数据类型优先集中放入共享类型文件，必须跨文件时使用 `import type`，避免引入运行时模块循环；递归树/图结构保留可空或集合边界，但不生成无限递归默认实例。输出的 TypeScript 类型必须在组件迁移前通过检查，以便后续组件使用真实数据契约生成 props/state，而不是由 LLM 重复猜测数据形状。

#### 4.4.3 单页面迁移

每个页面在静态资源和核心数据类可用后独立进入单页面迁移。WPF 源侧虽然可能由 XAML、code-behind 和相关 ViewModel 文件共同描述，但在迁移调度中统一视为一个页面迁移单元；目标侧以一个页面入口组件为主，可按工程约定拆出复用组件和样式文件。该过程分为“组件层级树迁移”和“页面整合”两步。

##### 4.4.3.1 组件层级树自底向上迁移

系统直接按当前页面组件依赖树的深度自底向上调度，反复执行以下循环：

1. **组件拆解/节点定位。** 在尚未迁移的节点中选择所有直接子节点已完成或本身为叶子的节点，定位其 XAML、code-behind/ViewModel 摘要及相关资源/数据/样式引用。
2. **目标组件定位。** 调用阶段2的标准组件规则映射或自定义组件功能总结/MUI 向量检索，获取候选 MUI 标准组件及完整契约。
3. **组件迁移。** 将当前节点 WPF 代码、必要局部上下文、可能使用的 MUI 标准组件、已迁移资源/数据类契约，以及当前节点所有直接子节点的迁移后代码和真实接口一并输入 LLM，生成当前 React 组件。
4. **节点验证与回填。** 对生成组件执行 TypeScript、MUI API、import、遗留模式和可渲染性检查；通过后将代码、props/state 接口和验证状态回填到组件树，作为其父节点的输入。失败时触发定向检索和局部修复，不允许未验证节点向上传播。

系统回到步骤1继续选择更浅一层的节点，直至组件依赖树根节点完成。这一“已迁移直接子节点代码→父节点生成上下文”的逐层传递是本研究所称“自底向上”的核心语义。事件、数据、模板和资源引用作为当前节点的附加上下文输入，不改变父子调度顺序。若资源依赖解析器发现 `recursive_component_ref`，则只阻塞该异常组件并保留人工处理记录；正常页面仍沿原组件树流程迁移。

##### 4.4.3.2 页面整合

组件树完成后，系统以根节点的迁移后代码、props/state 接口和验证状态为基础，输入阶段1已解析并在阶段3已迁移的资源依赖、数据依赖、样式依赖，以及必要的页面级 code-behind/ViewModel 摘要，调用 LLM 整合为完整 React 页面。

页面整合负责补齐页面入口、顶层数据/状态所有权、错误与空状态、页面级样式和跨组件事件协调，但不重新生成已通过验证的子组件。此时首先得到的是可独立运行和验证的“单页面版本”，多页面跳转逻辑留待后续联调。

#### 4.4.4 多页面迁移与联调

只有当全部单页面均完成组件树迁移、页面整合和单页面验证后，系统才进入多页面迁移。该过程不重写各页面主体，而是先沿主页面依赖树自底向上调度，让 LLM 基于已验证页面代码修改与页面联动相关的局部逻辑，包括：

- 页面跳转、路由配置和返回逻辑；
- 路由参数、查询参数和页面间数据传递；
- 主从页面、列表—详情、共享筛选条件和跨页面编辑流；
- 返回后刷新、共享状态与跨页面类型契约。

主树中由子页面先固定路由参数、返回值和对外类型，父页面随后生成或修改跳转调用。主树处理完成后，系统遍历额外页面依赖边表：对 B→A 等返回边补齐返回与刷新逻辑，对跨分支边补齐目标路由和参数传递，对次父边复用目标页面已经验证的路由契约。最后对完整页面组执行路由可达性、参数契约、跳转往返和关键跨页面交互测试。页面导航循环因此被拆为“主树父子边 + 额外返回边”，无需改变原有自底向上流程。

#### 4.4.5 阶段3的多Agent职责与状态传递

阶段3的多Agent系统至少覆盖：规则依赖分析与异常路由、全局调度，静态资源与数据类迁移，额外依赖边恢复，阶段2组件原语调用，组件节点审查与修复，页面整合，多页面联调与回归验证等职责。规则无法判断的动态引用可调用 LLM 依赖分析职责，但其输出必须带证据和置信度，并经过确定性验证。每个迁移单元和额外边必须保存 `pending`、`generated`、`merged`、`validated`、`blocked` 或 `unresolved` 等状态和输出契约；只有 `validated` 结果可传递给父组件或依赖页面。具体Agent数量可在后续实现中合并或拆分，但不得改变“规则优先”、“先拆后合”、“能力原语与顺序编排分离”、“组件树按深度自底向上”、“直接子节点代码向上注入”、“主页面树先处理、额外导航边后补全”和“单页全部完成后再多页面联调”等上位约束。

### 4.5 第二、三阶段共享的多层验证链

生成结果按固定顺序验证：

1. **TypeScript检查**：运行 `tsc --noEmit`，发现类型、import和组件契约错误；
2. **ESLint检查**：检查Hooks规则、未使用变量、列表key和可访问性规则；
3. **遗留模式检查**：通过TypeScript AST和文本规则检测残留 `{Binding}`、C#事件绑定、XAML资源表达式等；
4. **渲染检查**：在隔离环境中渲染组件，捕获运行时异常、控制台错误和空白页面；
5. **视觉检查**：对关键视口的迁移前后截图计算差异，并由人工抽样确认；
6. **交互检查**：执行表单输入、按钮、列表选择、弹窗和导航等关键脚本。

只有前三层通过才能计入“编译/静态通过”；视觉和交互通过用于评价更强的语义等价。论文必须分别报告这些指标，不能用编译通过代替迁移完成。

### 5.2 对比方法

#### 5.2.1 三条 baseline 与完整方法

1. **RuleTrans-MUI（传统规则适配基线）。** 当前未发现可直接运行于 WPF→React/MUI 的同行评审迁移工具，因此该基线不是冒用某一原工具，而是对传统“解析—中间树/元模型—固定映射—模板生成”范式的可复现适配。它使用通用 XML/XAML 解析、固定 WPF→MUI 控件表、布局/属性/Binding/事件/资源/显式导航规则和 TypeScript 模板，递归生成页面；不使用LLM、Embedding、RAG、Agent、语义摘要或学习式修复。自定义组件无规则时输出显式占位符并记失败，不能调用本文阶段2补齐。其思想主要参考遗留GUI逆向恢复、模型驱动GUI迁移及GWT→Angular工业迁移范式[E013][E014][E015][E018]，但所有 WPF/MUI 适配规则与原方法差异必须公开。
2. **LLM-Direct-Budget（纯LLM主基线）。** 输入为原始 XAML、同名/同目录 C# 文件、项目文件清单和固定目标环境说明；文件只按目录、文件名和上下文窗口做机械打包。若单次上下文无法容纳项目，则逐机械页面包独立生成，最后允许一次无结构化IR的工程合并调用。该方法不构造 Layout/Data/Dependency IR，不建立组件树或页面依赖树，不拆分组件，不检索MUI文档，不使用规则映射、多Agent、编译反馈修复或自底向上顺序。它与MigraUI使用同一基础模型，最大总输入/输出token预算近似匹配；预算是上限，不要求为耗尽预算而增加无意义调用。
3. **MigraUI-NoRAG（消融 baseline）。** 保留阶段1、组件拆分、自底向上顺序、直接子节点代码、依赖调度和固定上限修复，但不查询MUI知识库、不执行语义检索，也不向生成模型注入MUI文档；标准控件名称映射保留。该方法既作为第三条端到端baseline，也作为RAG贡献的核心消融。
4. **MigraUI（完整方法）。** 使用本文三阶段Pipeline、MUI RAG、自底向上组件迁移、直接子节点代码注入、主结构/额外边先拆后合和固定上限的工具反馈修复。

另设置 **LLM-Direct-Full** 作为可选成本敏感性分析：允许使用模型最大上下文和更高调用预算，但仍禁止IR、依赖图、RAG、组件拆分和工具反馈修复。它不能替代预算匹配的Direct基线进入主结论。UITrans、ArkTrans、Agentic Android→iOS和GUIMigrator因目标框架、输入语言与公开实现契约不同，不直接作为可执行端到端基线；它们只用于支持基线范式选择和结果讨论[E007][E008][E010][E009]。仓库级代码转换研究也表明，结构化分解与独立验证应作为需要单独消融的机制，而不能由公共适配器替基线补齐[E011][E043]。

#### 5.2.2 核心消融与降级

消融只保留能够分别对应核心方法假设、且有足够自动指标支撑的变体。NoRAG同时进入主baseline表，其余变体只进入消融表：

- **NoRAG：** 保留阶段1、组件拆分、自底向上顺序和修复，但不查询MUI知识库，LLM只依赖参数知识与固定目标版本说明，检验显式组件知识的增益；
- **NoComponentSplit（OneShotPage）：** 保留阶段1得到的页面级资源/数据/依赖上下文，但整个页面一次生成，不逐组件迁移，也不存在子节点代码传递，检验组件级分解的整体贡献；
- **TopDownComponent：** 保留相同组件集合和RAG，但按根到叶顺序生成，父节点无法使用已验证子节点代码，检验自底向上顺序；
- **NoChildCode：** 仍按自底向上顺序迁移，但父节点只接收子节点标识/接口摘要，不接收迁移后代码，单独检验直接子节点代码注入；
- **NoDependencySchedule：** 保留阶段2组件原语，但资源、数据类和页面按文件名顺序迁移，不使用主结构/额外边调度与后合，检验阶段1依赖分析和阶段3工程顺序；
- **NoRepair：** 保留三阶段首次生成结果，但不使用编译/测试反馈修复，检验工具闭环贡献。

`TextRAGOnly`、`ChunkTopK`、`NoSemanticSummary`、`NoExtraDependencyMerge`等细粒度变体只进入阶段2检索或特定失败类型的专项实验，不再占用端到端主表。这样可以避免大量高度相似的消融稀释主要结论。

#### 5.2.3 公共输入输出契约与公平性

所有方法接收相同源项目、当前React/TypeScript/MUI环境、同一空白目标工程骨架、相同允许依赖和相同二进制静态资源副本。公共骨架只包含 `package.json`、TypeScript/Vite配置、测试入口和空路由容器；不得包含由本文方法生成的组件、依赖图或目标实现。二进制资源可统一复制，因为LLM无法生成图片文件，但资源命名、import和引用重写仍由各方法完成。

所有方法必须输出同一目标目录契约，并由同一个只读评测器执行。公共适配器只能完成目录归一化、测试注入和日志收集，不得修复代码、补写路由、插入MUI组件或为基线恢复缺失依赖。评测清单、测试断言和参考截图在测试阶段对所有迁移方法隐藏。

生成式方法使用相同基础模型、温度、最大上下文和随机种子集合；主实验至少重复3次并报告均值和置信区间，不能挑选最佳一次。RuleTrans-MUI为确定性运行一次。除额外高预算敏感性分析外，LLM-Direct-Budget、各消融和MigraUI均报告总token、调用次数、墙钟时间和失败重试，防止把额外计算预算误写成方法收益。

### 5.3 评价指标

端到端指标必须对 RuleTrans-MUI、LLM-Direct-Budget、MigraUI-NoRAG、MigraUI及其余核心消融都可计算。设测试页面、自动可观察的源组件实例、确认导航边、预期截图状态对分别为 $N_p$、$N_{ci}$、$N_e$ 和 $N_s$。不要求方法输出相同的组件文件结构；评测器只观察统一目标工程的编译、DOM/可访问树、路由行为和截图。编译或渲染失败不得通过缩小后续分母获得更高分。

#### 5.3.1 端到端主指标：全部自动化、全部方法共享

**构建与运行。**

- **Page Compile Pass Rate（P-CPR）**：在统一页面入口和mock数据下通过TypeScript检查的页面数 / $N_p$；
- **Page Render Pass Rate（P-RPR）**：能够在统一页面测试壳中挂载且无未捕获运行时异常的页面数 / $N_p$；
- **Project Build Pass Rate（PBPR）**：同时通过固定TypeScript检查和生产构建的项目—运行次数 / 全部项目—运行次数。只有一个项目时必须同时报告P-CPR/P-RPR，不能用一个二值工程结果替代页面统计。

**组件实例复刻。**

- **Component Instance Replication Rate（CIRR）**：在最终渲染页面中，通过全部必需源侧实例契约断言的组件实例数 / $N_{ci}$。契约只包含跨实现可观察事实，如角色/可访问名称、文本或值、可见/启用/选中状态、必要父子区域和事件后的状态变化；不要求目标侧存在独立React组件文件。若所属页面编译或渲染失败，该页实例全部计失败。

CIRR进入端到端主表，因为RuleTrans-MUI和OneShotPage可能把多个源实例内联在一个页面文件中，无法统一计算依赖独立组件文件的门控指标。评测同时报告 $N_{ci}$ / 全部源组件实例数作为契约自动化覆盖，不再另造一个低解释性的覆盖率缩写；不可观察的装饰性、自绘或依赖外部系统的实例单列原因。

**页面调用关系。**

- **Navigation Edge Precision/Recall/F1（Nav-P/R/F1）**：规则解析目标React Router配置及 `Link`/`navigate` 调用后，与评测清单中的确认源导航边比较；主跳转、返回/交叉边分层报告；
- **Navigation Test Pass Rate（NTPR）**：通过自动路由测试的确认导航边数 / $N_e$。每条边由固定测试验证触发入口、目标页面和必要参数；返回、刷新或共享状态只在源边契约存在时断言。页面编译失败、测试不可执行或到达错误终态均计失败。

**视觉一致性。**

- **Screenshot Pair Coverage（SPC）**：获得有效且对齐的源—目标截图状态对数 / $N_s$；
- **Structural Similarity Index Measure（SSIM）**：有效截图对的像素结构相似度，计算定义遵循Wang等提出的结构相似性指标[E045]；
- **CLIP Similarity（CLIP）**：使用固定CLIP模型和预处理计算有效截图对的跨模态表征余弦相似度[E038]。

SSIM和CLIP只在有效截图对上计算，因此必须与SPC并列报告；不能只引用成功页面的条件均值。长期工业视觉GUI测试研究说明环境与维护成本会显著影响视觉证据解释[E021]，而Design2Code等前端生成基准也采用自动视觉指标与人工评价交叉校验[E083]。因此，截图环境继续固定WPF侧Windows/DPI/窗口/字体/主题/数据，以及React侧浏览器/视口/device scale factor/字体/主题/数据。

**成本。**

- 墙钟时间、峰值内存、LLM调用次数、输入/输出token和API成本；
- RuleTrans-MUI的LLM成本记为0，同时报告规则数量与不支持项；
- 人工接管比例只作为失败分析，不进入全自动主结论。

#### 5.3.2 方法内部诊断指标

以下指标不要求所有端到端基线具备，只用于解释MigraUI为何成功或失败，不能与主指标混为“整体优越性”证据。

**阶段1诊断。** 页面布局Parser、数据类Parser及资源依赖Parser分别在分层审计集上报告节点/成员/边的Precision、Recall和F1；五类依赖、主结构/额外边、闭环识别和处理策略分开统计。由于人工标边成本高，这些指标不进入端到端主表。

**阶段2诊断。** Standard Mapping Accuracy（SMA）评价标准组件规则定位；Custom Component Localization（CCL@K）、Recall@Nucleus、Mean Reciprocal Rank（MRR）和归一化折损累计增益（nDCG）评价自定义组件候选检索。MRR强调首个相关组件的排名[E093]，nDCG刻画多级相关性下的整体排序质量[E091]。Precision@Nucleus只在候选具有多重相关标签的审计子集上报告，不作为主指标。

**组件化实现诊断。** 对MigraUI、NoRAG、TopDownComponent、NoChildCode等确实输出独立组件的变体，报告Component Compile Pass Rate（C-CPR）、Component Render Pass Rate（C-RPR）、Component Contract Assertion Pass Rate（C-CAPR）、Interface Consistency Rate（ICR-UI）和Direct-child Reuse Consistency（DCRC）。这些指标不适用于RuleTrans-MUI、LLM-Direct或OneShotPage时标记为“不适用”，不得把不适用填成0再进行方法排名。

**工程资产诊断。** Static Resource Migration Rate（SRMR）、Data Type Migration Validity（DTMV）和Extra Dependency Restoration Rate（EDRR）用于NoDependencySchedule/NoExtraDependencyMerge专项实验；API Validity（APIV）和Legacy Residue Rate（LRR）用于错误归因。P-CPR已经覆盖多数不存在API和语法错误，因此APIV不再占用端到端主表。

#### 5.3.3 高成本补充评价

- **Multi-page Flow Pass Rate（MP-FPR）**：对实验前固定的少量关键跨页面流程执行Playwright端到端测试。它能发现逐边NTPR无法覆盖的连续参数传递、跨页编辑和返回刷新；类似地，ReuseDroid把测试可执行且到达正确目标GUI状态作为迁移成功条件[E019]。考虑环境准备和flaky成本，MP-FPR只作为重点流程补充；
- **局部视觉分析**：在能够建立源—目标实例对应的子集上报告LEMC以及Position、Size、Color、Text Integrity，用于分析布局误差来源。它依赖目标节点标识或可靠元素匹配，对不拆组件的基线覆盖不稳定，因此不进入主表；
- **VLM-JS与HSS**：只对按复杂度和自动指标分歧分层抽取的小型页面集执行。VLM Judge固定模型/prompt并先与盲法人工评分校准；若相关性不足，仅作定性案例分析。二者不参与主方法的显著性结论。

#### 5.3.4 最小自动化评测程序

1. **Build Runner**：为每页生成统一入口，执行P-CPR、P-RPR和PBPR；
2. **Contract Runner**：依据隐藏评测清单在最终页面DOM/可访问树上执行组件实例契约，计算CIRR；
3. **Navigation Evaluator**：静态抽取目标路由图计算Nav-P/R/F1，并生成MemoryRouter/React Testing Library逐边测试计算NTPR；
4. **Screenshot Runner**：驱动WPF与Playwright进入相同状态，生成截图对并计算SPC、SSIM和CLIP；
5. **Cost Logger**：记录每个方法—页面—运行的时间、内存、调用和token。

五个程序统一输出JSONL，至少包含 `method_id`、`run_id`、`page_id`、`source_instance_id/edge_id/state_id`、分母资格、通过状态、失败类别、环境信息和证据路径。评测器只读方法输出，不执行任何自动修复。

### 5.4 评估运行与统计分析

每个生成式方法在相同测试页面上以预注册的3个随机种子独立运行，RuleTrans-MUI运行一次。主表报告各次运行的均值、标准差和按业务模块聚类自助法得到的95%置信区间[E076]；不得只报告最佳运行。P-CPR、P-RPR、CIRR和NTPR等二值/比例结果分别使用成对页面、组件实例或导航边比较，并以McNemar检验或聚类bootstrap置信区间判断差异[E096]；SSIM/CLIP使用配对置换或Wilcoxon符号秩检验[E097]。多指标检验采用Holm校正[E022]，并同时报告效应量，避免只解释$p$值。

主结论首先比较RuleTrans-MUI、LLM-Direct-Budget、MigraUI-NoRAG和MigraUI；LLM-Direct-Full单列成本敏感性。NoRAG同时承担端到端baseline和RAG消融角色，其余核心消融在同一基础模型、同一输入集合和同一评测清单上与MigraUI成对比较。若某方法无法输出某页面，仍保留在P-CPR/P-RPR/CIRR/NTPR分母中；SSIM/CLIP缺失通过SPC体现，不进行均值插补。

人工评价只承担自动指标有效性核验：从测试集按页面复杂度、方法分歧和自动指标高/低区间分层抽取小型子集，由至少3名熟悉React和WPF的开发者独立盲评。标注者只能看到匿名化源/目标页面、截图和交互说明，不应知道方法名称或VLM结论。报告组内相关系数或加权Kappa[E094]并仲裁分歧；人工评分不扩展成全测试集主指标，也不用于调整测试集阈值。

## 7 案例分析

### 7.1 双向绑定迁移

源XAML：

```xml
<TextBox Text="{Binding UserName, Mode=TwoWay, UpdateSourceTrigger=PropertyChanged}" />
```

目标骨架：

```tsx
<TextField
  value={userName}
  onChange={(event) => setUserName(event.target.value)}
/>
```

规则层识别双向绑定并生成受控状态需求；检索层确定 MUI 输入组件的真实 `value`、`onChange` 和事件类型；生成层决定状态位于当前组件还是上移到父组件。

### 7.2 资源与主题迁移

`StaticResource` 不能简单替换为字符串。系统先通过资源图定位定义，再判断其对应颜色、尺寸、样式组合或ControlTemplate。颜色和尺寸可以映射为主题token，复杂模板需要转换为目标组件组合。缺失资源应被记录为阻塞项，而不是由模型随意编造。

### 7.3 复杂页面的分层迁移

对于包含筛选表单、数据表格和详情弹窗的页面，阶段2只定义“单个字段、按钮、表格或弹窗组件如何通过 MUI RAG 迁移”。真实执行由阶段3负责：先迁移当前页面使用的图片/样式与核心数据类，再沿组件依赖树从字段和按钮等叶子节点向表格、表单、弹窗和根节点推进。迁移表格时输入已迁移单元格/按钮代码，迁移表单时输入已迁移字段组件代码，直至根节点完成。随后融合页面级 ViewModel、资源、数据和样式依赖得到独立页面。若详情页另为独立路由，则等列表页与详情页均通过单页面验证后，再按页面依赖树修改跳转、路由参数和返回刷新逻辑。

## 8 讨论

### 8.1 编译通过不是迁移完成

TypeScript编译只能证明语法、类型和静态契约满足要求。错误的布局、未触发事件、状态更新时机错误和数据展示缺失均可能在编译通过后存在。端到端主评价把P-CPR/P-RPR/PBPR作为最低门槛，以架构无关的CIRR和NTPR判断组件实例与页面调用，以SPC+SSIM/CLIP补充视觉证据。C-CPR等独立组件指标只诊断本文组件化机制，VLM-JS/HSS只校准自动指标。各层分别报告，不以高视觉分数覆盖构建或行为失败。

### 8.2 组件级检索为何重要

一个目标组件的知识分散在概述、props表、事件说明和多个示例中。chunk级top-k可能只召回某段示例而漏掉限制条件。组件级聚合使检索评分仍基于局部证据，但生成上下文以完整组件为单位，符合“最终需要正确使用一个组件”的任务目标。

### 8.3 项目数据与保密

MUI 本身是公开目标组件库，但 WPF 源项目、业务页面、自定义控件和服务契约仍可能不能公开。系统应在受控环境中完成索引和生成，论文默认匿名化企业名称与业务信息。若源数据不可公开，应发布可运行框架、MUI知识库构建协议、匿名化统计和公开小型替代数据集，以支持方法层面的复现。

### 8.4 业务逻辑边界

ViewModel中的验证、状态和页面交互可部分迁移到前端；涉及数据库、权限和核心业务的逻辑应通过服务接口保留或后移。自动迁移系统必须输出未解决业务依赖，不应把缺少语义的信息隐藏为“已完成”。

### 8.5 增量迁移

实际项目会长期演进。源组件变化时，重新迁移该组件实例或共享组件类型的使用位置及其组件树祖先；页面导航变化时，更新对应依赖边，并重新验证受影响的页面组。目标组件库API变化时，利用检索来源和使用清单定位需要重新验证的页面。

## 9 有效性威胁

### 9.1 内部有效性

- 模型、prompt和温度可能改变结果；应记录实际配置并重复实验；
- 组件知识库文档质量可能成为混杂变量；应报告文档覆盖率和源码补全方式；
- 页面布局、数据类或资源依赖 Parser 的漏节点/漏边会通过调度链传播到阶段2–3；需对三类Parser分别建立分层人工核验集，并保留未解析动态依赖。

### 9.2 外部有效性

- 单个企业WPF项目不能代表所有遗留系统；应补充公开小型项目或跨模块分析；
- 目标组件库的成熟度会影响迁移难度；结论不应直接外推到任意React组件库；
- 本文结论仅针对 WPF→React/MUI，不自动适用于 WinForms、Qt 或其他框架迁移。

### 9.3 构念有效性

- 编译率不能代表功能等价；已增加源侧组件契约、导航边、关键流程、视觉和人工评价；
- CIRR取决于源侧实例契约是否充分；必须报告 $N_{ci}$ / 全部实例数、人工/不支持项，并抽样核验自动生成测试；
- 截图相似度可能受字体、DPI、动画、平台默认样式和数据影响；需固定环境、报告SPC并同时使用全局与局部指标；
- VLM Judge具有模型偏差与非确定性；应记录模型和prompt，在盲法人工子集上校准，不能作为唯一视觉指标；
- 人工语义评分带有主观性；需盲评、统一量表和一致性分析。

### 9.4 结论有效性

- 正式结果需报告分子、分母、方差、置信区间和显著性检验；
- 页面之间可能因共享组件而非独立，应采用按模块聚类或分层统计；
- [MOCK] 数据只用于规划，不能参与最终推断。

## 10 结论与未来工作

本文研究一种面向 WPF→React/MUI 的三阶段前端UI迁移方法。阶段1由页面布局解析器、数据类解析器和资源依赖解析器生成逐页面组件依赖树、各类主依赖结构、统一额外依赖边表和资源依赖映射表。组件树只表达 XAML 实例的布局包含关系，因此可直接按层级深度调度；组件类型、事件、数据、模板和资源引用作为附加事实保存。页面、数据、资源、样式和模板中的闭环关系统一采用“规则解析—先拆迁移—后合引用—工具验证”：规则先确定主关系和闭环边，LLM仅辅助动态或语义不明的引用；各节点迁移后，再按类型恢复引用、提取共同基础项或显式阻塞。阶段2将组件作为最小迁移单元，对 WPF 标准组件使用规则映射，对自定义组件使用 LLM 功能总结和 MUI 向量检索，再以知识增强 LLM 生成 React 组件。阶段2只定义单组件迁移原语，不单独声称具备自底向上顺序。阶段3先迁移静态资源和 C# 核心数据类，再沿组件层级树自底向上调用阶段2原语，将所有直接子节点迁移后代码注入父节点，并以根节点融合资源、数据和样式依赖得到完整页面。全部单页面完成后，系统先沿主页面依赖树自底向上生成主导航逻辑，再根据统一额外依赖边表补齐返回、交叉跳转和其他引用。阶段2的 RAG 能力与阶段3的顺序编排相互配合，但在写作和实验中必须区分其职责与贡献。

当前已实现RuleTrans-MUI、预算匹配的LLM-Direct-Budget、MigraUI-NoRAG、公共目标骨架和隔离运行目录，并以离线契约、单页面/单控件LLM smoke及RuleTrans真实构建验证其入口。下一步冻结隐藏评测清单，以同一Build/Contract/Navigation/Screenshot Evaluator运行三条baseline与完整MigraUI；随后完成NoComponentSplit、TopDownComponent、NoChildCode、NoDependencySchedule和NoRepair其余五个核心消融，以P-CPR/P-RPR/CIRR/Nav-F1/NTPR/SPC/SSIM/CLIP及成本形成主证据。局部视觉、关键流程、VLM Judge和人工评价只在分层子集上补充。最后以真实迁移记录替换全部 [MOCK] 数据并完善复杂资源、动态模板和跨组件状态的错误路由。在融合论文中，本课题作为“遗留软件资产再生”路径，与C++习语课题共同服务于代码可复用性增强，但不假设两者存在直接数据流。
